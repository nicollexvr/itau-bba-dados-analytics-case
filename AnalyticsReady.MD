O projeto foi estruturado com foco em transformar bases operacionais fragmentadas em um modelo analítico confiável para análise de pipeline comercial de operações de Deal & Capital Markets (DCM), utilizando Excel, Power Query, tabelas dinâmicas e dashboard executivo. Desde o início, o desenvolvimento foi guiado pelo princípio de que, em um contexto financeiro, a confiabilidade dos dados é tão importante quanto os indicadores finais gerados.

A primeira etapa do trabalho consistiu na análise estrutural das bases presentes no arquivo do case, identificando a granularidade de cada tabela, seus relacionamentos e os principais problemas de qualidade de dados. O projeto consolidou tabelas com objetivos distintos: um log de interações comerciais (interactions_log), uma tabela principal de pipeline (deals_pipeline), uma tabela mestre de clientes (company_master), além das tabelas auxiliares de taxas cambiais (fx_rates) e médias históricas de fee (Media_Tipo e Media_Tipo_Cargo). Cada uma dessas estruturas possuía granularidade própria e exigia tratamento específico para garantir integridade analítica.

Durante a análise inicial, foram identificadas inconsistências críticas que comprometiam diretamente a utilização dos dados para tomada de decisão. Na tabela interactions_log, as datas estavam registradas em formatos diferentes dentro da mesma coluna, incluindo registros finalizados com “Z” no padrão UTC ISO 8601 e registros contendo timestamp completo com timezone. Isso impedia a conversão direta para o tipo DATA no Power Query e gerava erros silenciosos durante os cálculos temporais. Para resolver esse problema, foi aplicada uma padronização utilizando a extração dos dez primeiros caracteres da string de data, preservando apenas o trecho correspondente ao formato AAAA-MM-DD, seguido da conversão para valor de data válido no Excel. Essa abordagem permitiu converter 100% dos registros sem perda de linhas.

Outro problema identificado estava relacionado ao encoding da tabela company_master. Alguns nomes de clientes apresentavam caracteres corrompidos, impossibilitando joins consistentes entre as tabelas. O tratamento foi realizado diretamente no Power Query por meio da padronização do encoding para UTF-8 e correções residuais manuais nos casos em que a substituição automática não foi suficiente. Essa correção foi essencial para evitar registros órfãos durante os relacionamentos entre as tabelas fato e dimensão.

Na tabela deals_pipeline, foram identificados múltiplos problemas de tipagem. Datas importadas como texto impediam cálculos de ciclo de vida e aging do pipeline, enquanto a coluna de probabilidade possuía separadores decimais mistos, alternando entre “.” e “,”. O Power Query interpretava parte dos registros como texto e parte como número, distorcendo os cálculos sem apresentar erro explícito. Para resolver isso, foi criada uma coluna de correção utilizando substituição de separadores decimais via Text.Replace, seguida da conversão uniforme para tipo decimal. A coluna original foi preservada para garantir rastreabilidade das transformações.

A normalização cambial foi um dos pontos centrais do projeto. Os valores financeiros das operações estavam registrados em BRL, USD e EUR sem qualquer conversão padronizada, o que inviabilizava qualquer análise financeira consolidada. Para resolver isso, foi construída uma tabela auxiliar de FX Rates contendo taxa por moeda e data. O tratamento consistiu em realizar merge entre deals_pipeline e fx_rates utilizando as chaves Data + Moeda, expandindo posteriormente a taxa correspondente e criando a coluna Valor Negócio BRL. Essa padronização garantiu que todos os cálculos financeiros subsequentes fossem realizados em uma única moeda de referência, preservando comparabilidade e consistência analítica.

Além dos problemas estruturais, também foram identificadas inconsistências operacionais relevantes para análise de negócio. Registros classificados como NO_SHOW e Sem Resposta continham duração de interação e anotações preenchidas, indicando esforço operacional real mesmo sem retorno formal do cliente. Também foram encontrados possíveis falsos positivos e falsos negativos no pipeline, como operações marcadas como “Proposta Aceita” sem evidência operacional correspondente. Esses registros não foram excluídos da base; foram isolados analiticamente para permitir avaliação posterior da área de negócio, evitando interferência irreversível nos dados originais.

Com os dados tratados, foi construída a camada analítica do projeto. O modelo adotado separa claramente tabelas fato e dimensão, seguindo uma abordagem analytics-ready compatível com estruturas de Data Warehouse. A tabela deals_pipeline foi tratada como tabela fato principal do pipeline comercial, com granularidade definida como “1 linha = 1 deal em determinado estágio”. Já a tabela interactions_log foi estruturada como tabela fato operacional de interações, com granularidade “1 linha = 1 interação comercial”.

As dimensões foram organizadas a partir das tabelas auxiliares e cadastrais existentes no case. A company_master foi utilizada como dimensão de clientes, contendo cadastro mestre e atributos de segmentação. A tabela fx_rates foi utilizada como dimensão cambial para normalização monetária. As tabelas Media_Tipo e Media_Tipo_Cargo foram utilizadas como apoio para imputação hierárquica de fee_bps, permitindo preencher operações sem fee informado a partir da média histórica por tipo de negócio e cargo bancário.

A imputação de fee_bps foi construída em três níveis hierárquicos. Quando o valor original existia, ele era preservado. Quando ausente, o modelo buscava primeiro a média histórica por tipo de negócio e cargo bancário (Media_Tipo_Cargo). Caso ainda não houvesse cobertura suficiente, era utilizada a média por tipo de negócio (Media_Tipo). Essa abordagem evitou utilização de médias globais, reduzindo distorções em produtos financeiros com estruturas de fee diferentes.

Com a estrutura consolidada, foram criadas métricas derivadas para análise executiva do pipeline. Entre elas, destacam-se receita esperada (expected_fee_brl), revenue ajustado por probabilidade, cycle time, aging, win rate, ticket médio e indicadores de retrabalho operacional. Todas essas métricas foram calculadas sobre os dados já padronizados e normalizados, garantindo consistência entre os indicadores apresentados no dashboard.

O fluxo completo do projeto foi desenvolvido utilizando Power Query como camada principal de ETL. Essa decisão permitiu manter todas as transformações registradas como etapas auditáveis e reproduzíveis, separando completamente os dados brutos da camada analítica. O dashboard final foi construído a partir da tabela consolidada resultante dos merges e transformações, utilizando tabelas dinâmicas e gráficos dinâmicos para visualização executiva dos KPIs do pipeline.

Como proposta de estrutura analytics-ready, o modelo final recomenda formalmente a separação entre tabelas fato e dimensão, utilizando deals_pipeline e interactions_log como fatos principais, e company_master, fx_rates, Media_Tipo e Media_Tipo_Cargo como dimensões e tabelas auxiliares analíticas. A granularidade das tabelas foi preservada para evitar duplicidade de registros e garantir rastreabilidade operacional. As chaves utilizadas no modelo seguem a estrutura original do case, principalmente deal_id, interaction_id, client_id, além das chaves compostas de data e moeda utilizadas nos relacionamentos cambiais.
